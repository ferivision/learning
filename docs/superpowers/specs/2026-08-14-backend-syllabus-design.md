# Design: Backend Engineering Syllabus (`roadmap-backend/`)

## Goal

Populate `roadmap-backend/` with a 15-phase, 103-topic backend engineering syllabus. `roadmap-backend/README.md` is the roadmap index (already authored by the user, copied verbatim — not regenerated). `roadmap-backend/syllabus/phase-01-*.md` through `phase-15-*.md` are the detailed lesson files, one per phase, each explaining every topic listed under that phase in the README.

This is a content-generation task, not a code feature — the "design" here is about structure, consistency, and how the large volume of content gets produced without truncation, not about system architecture.

## Scope

- Create `roadmap-backend/README.md` — exact copy of the content the user pasted in conversation. No edits.
- Create `roadmap-backend/syllabus/phase-01-authentication-authorization.md` … `phase-15-interview-thinking.md` (15 files).
- Topic list per phase is fixed by the user's original master prompt (103 topics total, phase 1–15). No topics added or removed. This list is reproduced in full in the Topic Reference section below so the implementation plan doesn't need to re-derive it from chat history.

## Per-topic content structure (mandatory, every topic in every phase)

```markdown
## <Number>. <Topic Name>

### Apa itu?
### Kenapa dibutuhkan?
### Cara Kerja
### Contoh Kode — Go
### Contoh Kode — Node.js
### Trade-off & Pitfall
### Kapan Dipakai
### Sering Ditanya Saat Interview
```

Rules:
- Language: casual Bahasa Indonesia mixed with untranslated technical terms (goroutine, connection pool, etc).
- Code blocks: real, valid, idiomatic — not pseudocode. Go and Node.js (Express + the standard libraries listed under Shared Example Project below).
- Skip the two code sections only for topics that are purely conceptual (e.g. CAP Theorem, all of Phase 15). Every topic with a technical implementation gets both code blocks.
- Every phase file opens with:
  ```markdown
  # Phase XX — <Phase Name>

  > Bagian dari [Backend Engineer Roadmap](../README.md)

  ---
  ```
- Every phase file (except phase-15) closes with:
  ```markdown
  ---

  **Selanjutnya:** [Phase XX+1 — <Next Phase Name>](./phase-XX+1-xxx.md)
  ```

## Shared example project: OrderFlow

All Go and Node.js code samples across all 15 phases live in one fictional, continuously-evolving codebase — an e-commerce order API — rather than disconnected snippets. This lets later phases reference or extend earlier phases' code (e.g. Phase 4's cache-aside example wraps the same `GetProductByID` introduced in Phase 3).

**Domain / entities**: `User` (id, email, password_hash, role), `Product` (id, name, price, stock), `Order` (id, user_id, status, total, version), `OrderItem` (order_id, product_id, qty, price), `Payment` (id, order_id, status, idempotency_key).

Chosen because it naturally exercises nearly every phase without forcing it: auth/RBAC (Phase 1), IDOR checks on order ownership (Phase 2), transactions/locking on stock (Phase 3), product-catalog caching (Phase 4), payment/order events (Phase 5, 14), goroutine/worker-pool order processing (Phase 6), service-to-service order↔payment↔inventory calls (Phase 7–8), health/circuit-breaker around the payment provider (Phase 9), and product-image upload (Phase 14).

**Stack**:
- Go: standard `net/http` or `chi` router, `pgx` (Postgres), `golang-jwt/jwt` (JWT), `golang.org/x/crypto/bcrypt`, `go-redis/redis` (Redis).
- Node.js: Express, `jsonwebtoken`, `bcrypt`, `pg`, `ioredis`.

## Cross-phase continuity mechanism

Each phase is generated by its own subagent (see Execution below), so no single agent sees every prior phase's full file. To keep the "one evolving project" feel without ballooning every prompt with 14 previous files:

- Each phase's subagent prompt includes a short **carry-forward API summary** — just the function/struct signatures introduced in earlier phases that this phase's topics are likely to touch (e.g. Phase 4's prompt gets `GetProductByID(ctx, id) (*Product, error)` from Phase 3, not Phase 3's full file).
- After each phase subagent finishes, the orchestrator (main session) skims the produced file and appends any newly-introduced reusable function/struct signatures to a running carry-forward list, passed to the next phase's prompt.
- This carry-forward list is working state for execution, not part of the committed docs.

## Execution approach

- One subagent per phase file, dispatched **sequentially** (phase-01 must finish and be saved before phase-02 starts) — this avoids single-response output truncation on large files and preserves the carry-forward summary chain.
- Each subagent writes its file directly to disk via the Write tool and returns; it is not expected to paste the full content back into the conversation.
- Each subagent's prompt is self-contained: phase number/name, its exact topic list, the mandatory section structure, the OrderFlow domain + stack, the carry-forward summary so far, and the header/footer template.

## Out of scope

- No changes to the root `README.md` or repo structure outside `roadmap-backend/`.
- No CI, tooling, or test automation — this is documentation content only.
- No topics added beyond the fixed 103-topic list.
